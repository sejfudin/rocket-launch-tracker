# Styling, theming and design system

We use [Tailwind](https://tailwindcss.com/) for styling. To improve working with it, we suggest installing the VSCode extension (specified in recommended extensions if you use VSCode) and get familiar with how to quickly inspect classes. We also use the Biome plugin that sorts classes and an eslint plugin that warns you about using non-Tailwind classes, which prevents typos.

Tailwind is used because it is compatible with Povio's design system, it is easy to use, and performant.

## Design system

The template is using Povio internal design system (also known as Atlas) as the basis. The system is drawn in Figma and specifies design atoms (colors, spacings, typography) and components (buttons, dropdowns, ...). The idea behind this system is that it can be used to start a new project quickly by copying the base Figma file and readjusting the colors, typographies, etc. At the same time, this project implements that Figma, so that the same changes as they are done in Figma can also be applied here in code to achieve the same result. Finally, the Figma and the code follow the same terminology, making it easier to implement designs.

Here's the Figma of the base system, which is also implemented in this project: [Figma Atlas](https://www.figma.com/design/L55jgNE1TK1PAjQfUDnNjZ/Web-Project----Design-System?node-id=13203-16&p=f&t=TXeYoYWivcMq23vs-0).

Please note that the design system is not mandatory to use - it will be used on all new projects that start at Povio, but many times you might still receive designs from third party designers. Instructions below will detail when to use it and when not to use the system, and what to do if you aren't using it.

### Design atoms and theme auto-generation

Design tokens from the system are specified in the tailwind theme `theme.css`. They are actually imported using Pixel2Code plugin using this procedure:

<div className="[&>ol]:list-decimal">
1. Inside `src/styles/base.css` write all the configuration that is not in Figma. Sensible defaults are provided. The tailwind config will use this base config as a preset. That is why there are some empty properties here which override the default tailwind values and then tailwind config only extends them.
2. In Figma, use the **Pixel to Code** plugin. Search for it in the plugins sidebar (as long as you're part of Povio organization, you should find it).
3. Click on it and select Export config.
4. Choose Tailwind V4.
5. Choose correct types for each font (serif/sans/mono) - for Google Fonts no need to select the type as we can get it from Google api - and click Export.
6. Copy the config and paste it into the `src/styles/theme.css` file.
7. Check the `fontFamily` section of the config. You should see a couple of CSS variables being referenced. Make sure to declare these variables to point to your font family (without the fallback). Check [fonts](./fonts.md) for more information.
8. If you need to add any one-off style into the theme, add it to `src/styles/base.css`. Also enter breakpoints into this file (or keep the default ones).
9. If you spot any bugs with Pixel to Code, please report them to the template maintainers.
</div>

If you are not using Povio's design system, you can delete `theme` folder and adapt the theme to match your project. Use the autogenerated theme as your guide.

### Tailwind plugins

If you are using additional Tailwind plugins, you can define them in `src/styles/base.css`.

### Design components

The components are stored in the `packages/ui/src/components` folder and are written using React Aria. They are themed in exact accordance with the design system, using the same names (like button widths, typography sizes, ...). ### Overriding styling of UI components

`@povio/ui` package exposes `UIStyle.Provider` that allows you to override cvas and typographies for components. It's important that the provider is declared before any other providers that might use it (like Confirmation or Modal providers).
You can add overrides in `src/styles/overrides` folder with additional subfolders to separate them a bit (buttons, fonts, inputs).

In general, designers shouldn't change the components but sometimes they have no choice. One of the more common changes is to the text styles (typographies).

Pixel2Code supports exporting text styles directly using the following procedure:

<div className="[&>ol]:list-decimal">
1. Click on **Pixel to Code** plugin and select Export config.
2. Choose Typography.
3. Copy the generated code to `src/styles/overrides/typography.cva.ts`.
4. In `src/pages/__root.tsx` in the `Providers` component add the following code:
  ```tsx
  import { UIStyle } from "@povio/ui";
  import { typography } from "@/styles/overrides/typography.cva"
  // ...
      {
        provider: UIStyle.Provider,
        props: { config: { typography: { cva: typography } } },
      },
  // ...
  ```
5. In `src/types/ui.d.ts` add the following inside `declare module "@povio/ui"` for overriding typography types
  ```tsx
  interface TypographyVariantProps {
    size?: VariantProps<typeof typography>["size"];
    sizeMobile?: VariantProps<typeof typography>["sizeMobile"];
  }
  ```
</div>
---
You can do the same for other components like buttons.

```tsx
import { UIStyle } from "@povio/ui";
// ...
    {
      provider: UIStyle.Provider,
      props: { config: { button: { cva: customButton, typography: buttonTypography } } },
    },
// ...
```

The component cva should be a normal cva, but make sure that you use the same variant names (you can add additional values to each variant or define your own styles for them).

```tsx
export const customButton = cva(["flex items-center justify-center", uiOutlineClass], {
  variants: {
    width: {
      fill: "w-full",
      hug: "w-auto",
    },
    size: {
      "extra-small": "rounded-button-rounding-m px-button-side-s py-button-height-s",
      small: "rounded-button-rounding-m px-button-side-m py-button-height-m",
      default: "rounded-button-rounding-m px-button-side-l py-button-height-l",
      large: "rounded-button-rounding-m px-button-side-xl py-button-height-xl",
    },
    color: {
      primary: "",
      secondary: "",
      success: "",
    },
    variant: {
      contained: "",
      outlined: "",
      subtle: "",
    },
  },
  defaultVariants: {
    width: "fill",
    color: "primary",
    variant: "contained",
  },
});
```

To make sure TypeScript will work nicely with the new additions of variant values, extend the `@povio/ui` types.
Create `src/types/ui.d.ts` file or add the types to the existing ones if it already exists:

```ts
import "@povio/ui";
import { VariantProps } from "class-variance-authority";

import { customButton } from "...";

declare module "@povio/ui" {
  interface ButtonVariantProps {
    color?: VariantProps<typeof customButton>["color"];
  }
}
```

To override the typography, define with the `compundMapper` function from `@povio/ui` (the same way it's defined in `button.cva.ts` inside the `@povio/ui` package):

```ts
export const buttonTypography = compoundMapper<TypographyVariantProps, ButtonVariantProps>({
  defaultVariants: {
    size: "default",
  },
  compoundVariants: [
    {
      size: "extra-small",
      value: {
        size: "label-2",
        variant: "prominent-1",
      },
    },
    {
      size: "small",
      value: {
        size: "label-2",
        variant: "prominent-1",
      },
    },
    {
      size: "default",
      value: {
        size: "label-2",
        variant: "prominent-1",
      },
    },
    {
      size: "large",
      value: {
        size: "label-2",
        variant: "prominent-1",
      },
    },
  ],
});
```

### Alternatives

The design system can only be used if the design team is using it. This depends on external factors. If the design system is not being used on the design side, it might be difficult to translate Figma designs into the code using the existing system unless the provided Figma designs are conceptually designed in a similar manner.

In most such cases, you will need to implement your own design system. In this case, you can start from a blank `tailwind.config.ts`. Regarding the UI components, you could keep their functionality and restyle them according to your own needs.

### What about Material UI, Bootstrap and other UI libraries?

Material UI and Bootstrap are opinionated. They come with their own design system and components. It is not recommended to use them on any project with its own custom designs, unless that design is directly derived from the design system of the aforementioned libraries. In most cases, the most flexible solution is having an opinionated UI library (like React aria) and a styling solution (like Tailwind).

## Guidelines

Here are some guidelines for theming and styling:

- Avoid hardcoding values inside classes (eg. `p-[3rem]`). Instead, define them in the theme.
- Name colors and fonts semantically. For example, if the primary color is blue, don't name it `blue`, but `primary`. This way, if the color changes, you don't have to change the class names. Make sure that the designers follow this practice as well so that Figma and code are in sync.
- Use rems for font sizes, spacings and paddings/margins. This is important for accessibility.
- To avoid repeating the same classes over and over again, separate them into components.
- If you need to use different font families per typography type (headings, title...), you can apply font family classname (`font-primary`, ...) for specific size or variant in the Typography.tsx in the `compoundVariants` section of the CVA config.
